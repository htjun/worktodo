# Worktodo Shared Task Model

**Status:** Approved design contract for future domain, SQLite, Raycast, menu-bar, and MCP implementation.

This document defines one adapter-independent model. It does not add product persistence. Future
clients must call the same domain operations and must not reinterpret placement, lifecycle, due
values, Today membership, priority, or ordering.

## Shared conventions

- IDs are stable, opaque, lowercase UUID v4 strings generated by the domain layer. They carry no
  ordering or ownership meaning and never change.
- Timestamps are integer Unix epoch milliseconds in UTC. `createdAtMs` is immutable;
  `updatedAtMs` advances on every state change and never moves backwards.
- User-visible names and task titles are Unicode strings trimmed by the domain layer and rejected
  when empty. Names are not unique; IDs establish identity.
- Notes are one plain-text string on a task. The empty string means no note. URLs remain ordinary
  note content and are not separate entities.
- Every operation uses one transaction and either returns the documented result or one bounded
  error without changing state.
- Every final ordering tie is resolved by lowercase UUID using bytewise ascending comparison. This
  matches SQLite `BINARY` collation for the permitted ID format.

## Entities

### Project

| Field         | Required | Meaning                                               |
| ------------- | -------- | ----------------------------------------------------- |
| `id`          | Yes      | Stable opaque ID.                                     |
| `name`        | Yes      | Non-empty display name.                               |
| `position`    | Yes      | Non-negative integer manual order among all projects. |
| `createdAtMs` | Yes      | Creation instant.                                     |
| `updatedAtMs` | Yes      | Most recent project change.                           |

Projects are flat. They cannot own other projects. Duplicate names are allowed.

### Section

| Field         | Required | Meaning                                                  |
| ------------- | -------- | -------------------------------------------------------- |
| `id`          | Yes      | Stable opaque ID.                                        |
| `projectId`   | Yes      | ID of the one project that owns the section.             |
| `name`        | Yes      | Non-empty display name.                                  |
| `position`    | Yes      | Non-negative integer manual order within the project.    |
| `createdAtMs` | Yes      | Creation instant.                                        |
| `updatedAtMs` | Yes      | Most recent section change or ownership-preserving move. |

Sections cannot nest. A section cannot exist without its owning project and cannot move to another
project. Renaming is the only section identity-preserving change; moving its tasks and creating a
new section is required to represent a different owner.

### Task

| Field           | Required | Meaning                                                         |
| --------------- | -------- | --------------------------------------------------------------- |
| `id`            | Yes      | Stable opaque ID.                                               |
| `title`         | Yes      | Non-empty task title.                                           |
| `notes`         | Yes      | Plain text; defaults to the empty string.                       |
| `priority`      | Yes      | One of `none`, `low`, `medium`, or `high`.                      |
| `position`      | Yes      | Non-negative integer manual order within the current placement. |
| `projectId`     | No       | Owning project for project and section placements.              |
| `sectionId`     | No       | Owning section for section placement only.                      |
| `due`           | Yes      | Tagged due value defined below; defaults to `none`.             |
| `createdAtMs`   | Yes      | Creation instant.                                               |
| `updatedAtMs`   | Yes      | Most recent task change.                                        |
| `completedAtMs` | No       | Completion instant; `null` means incomplete.                    |
| `trashedAtMs`   | No       | Trash instant; `null` means not trashed.                        |

The note is part of the task rather than a separate entity. Completion and Trash are independent
timestamps: a completed task can also be trashed without losing its completion state.

## Placement

A task has exactly one placement, derived only from its two placement fields:

| Placement       | `projectId` | `sectionId` | Validity rule                                       |
| --------------- | ----------- | ----------- | --------------------------------------------------- |
| Inbox           | `null`      | `null`      | Always valid.                                       |
| Direct project  | Project ID  | `null`      | The project exists.                                 |
| Project section | Project ID  | Section ID  | Both exist and the section belongs to that project. |

No other combination is valid. In particular, a section without a project, a missing parent, and a
section owned by a different project are rejected as `INVALID_PLACEMENT`. Inbox is an explicit
domain placement even though storage represents it with two null foreign keys.

### Placement decision table

| Example                                        | Result              |
| ---------------------------------------------- | ------------------- |
| `projectId = null`, `sectionId = null`         | Inbox               |
| Existing project, `sectionId = null`           | Direct project      |
| Existing project and its existing section      | Project section     |
| `projectId = null`, existing section           | `INVALID_PLACEMENT` |
| Missing project, `sectionId = null`            | `INVALID_PLACEMENT` |
| Existing project and missing section           | `INVALID_PLACEMENT` |
| Existing project and another project's section | `INVALID_PLACEMENT` |

## Priority and canonical ordering

Priority is a closed vocabulary with the following descending rank:

| Priority | Rank |
| -------- | ---: |
| `high`   |    3 |
| `medium` |    2 |
| `low`    |    1 |
| `none`   |    0 |

The canonical order for projects is `(position ASC, createdAtMs ASC, id ASC)`. Sections use the
same tuple within one project. Ordinary task lists use
`(priority rank DESC, position ASC, createdAtMs ASC, id ASC)`. Today has the additional due ordering
defined below. Search relevance may precede the ordinary task tuple, but equal relevance must use
the complete ordinary tuple.

Positions are non-negative signed 64-bit integers. Creation and movement append an item to its
target placement. A future implementation may leave gaps for manual reordering; if a midpoint is
unavailable or append would overflow, it must renumber that placement to `1024, 2048, ...` in the
same transaction before applying the operation. Equal positions are valid and remain deterministic
because every order ends with creation time and ID.

## Lifecycle and movement

Task lifecycle is derived from the two independent timestamps:

| State               | `completedAtMs` | `trashedAtMs` |
| ------------------- | --------------- | ------------- |
| Active, incomplete  | `null`          | `null`        |
| Active, completed   | Timestamp       | `null`        |
| Trashed, incomplete | `null`          | Timestamp     |
| Trashed, completed  | Timestamp       | Timestamp     |

Trash preserves the complete task row, including completion and placement. Restore clears only
`trashedAtMs`; therefore restoring a completed task produces an active, completed task. Reopening
is a separate operation that clears `completedAtMs`.

For a real state change, the domain sets `updatedAtMs` to at least one millisecond after its previous
value, using the operation instant when that is later. A documented no-op preserves every field and
timestamp. Complete and Trash use that same effective monotonic timestamp for `completedAtMs` or
`trashedAtMs`; they do not retain a clock value that precedes the task's prior update. `createdAtMs`,
`completedAtMs`, and `trashedAtMs` never exceed `updatedAtMs`.

### Task transition table

| Current state      | Operation          | Result                                                            |
| ------------------ | ------------------ | ----------------------------------------------------------------- |
| Missing            | Any task operation | `NOT_FOUND`; no state change.                                     |
| Active, incomplete | Complete           | Set `completedAtMs` and advance `updatedAtMs`.                    |
| Active, completed  | Complete           | No-op; preserve the original completion timestamp.                |
| Active, completed  | Reopen             | Clear `completedAtMs` and advance `updatedAtMs`.                  |
| Active, incomplete | Reopen             | No-op.                                                            |
| Either active      | Trash              | Set `trashedAtMs`; preserve completion, placement, and content.   |
| Either trashed     | Trash              | No-op; preserve the original Trash timestamp.                     |
| Either trashed     | Restore            | Clear `trashedAtMs`; preserve completion, placement, and content. |
| Either active      | Restore            | No-op.                                                            |
| Either active      | Move               | Validate the target, append there, and advance `updatedAtMs`.     |
| Either active      | Move to same place | No-op unless an explicit new manual position is also requested.   |
| Either trashed     | Complete or reopen | `TASK_TRASHED`; restore first.                                    |
| Either trashed     | Move or edit       | `TASK_TRASHED`; restore first.                                    |

Create accepts exactly one valid placement and creates an active, incomplete task. A move accepts
Inbox, a direct project, or a project section using the same placement validation as creation. It
changes both placement fields together and appends to the target; partial placement updates never
exist. An invalid target returns `INVALID_PLACEMENT` without changing the task.

The bounded operation errors for this initiative are:

- `INVALID_ARGUMENT` for malformed IDs, text, priority, timestamps, or positions;
- `INVALID_DUE_VALUE` for a malformed or inconsistent due value;
- `INVALID_PLACEMENT` for missing, incomplete, or cross-project placement references;
- `NOT_FOUND` when the target task, project, or section ID does not exist; and
- `TASK_TRASHED` when an operation requires an active task.

Storage-specific constraint names, SQLite codes, and adapter exceptions must be mapped to this set
inside the shared domain/storage boundary. Unexpected storage failures remain infrastructure errors;
they are not silently converted into a successful operation.

### Project and section removal

There is no ordinary permanent-delete task operation. Task removal means Trash; a future explicit
purge or retention policy requires a separate product decision.

Removing a section is one transaction: lock the write, load all of its tasks including completed and
trashed tasks, append them to the section's project as direct-project tasks, then delete the empty
section. Tasks are appended in `(position ASC, createdAtMs ASC, id ASC)` order. All task content and
lifecycle timestamps survive.

Removing a project is one transaction: lock the write, load all tasks in the project and its
sections including completed and trashed tasks, append them to Inbox, delete the empty sections, and
then delete the project. Direct-project tasks precede section tasks; sections use their canonical
project order and tasks within each source use `(position ASC, createdAtMs ASC, id ASC)`. This makes
the merged append deterministic while preserving every task's content and lifecycle. After either
parent-removal operation, restoring a trashed task uses its already-normalized direct-project or
Inbox placement.

Foreign keys use `ON DELETE RESTRICT`, so bypassing these domain transactions cannot orphan or
silently delete tasks. Repeating removal after the parent is gone returns `NOT_FOUND`.

## Due values

Due is a closed tagged union:

```ts
type DueValue =
  { kind: "none" } | { kind: "allDay"; date: string } | { kind: "timed"; instantMs: number; timeZone: string };
```

- `none` carries no date, instant, or timezone.
- `allDay.date` is a real Gregorian calendar date from `0001-01-01` through `9999-12-31`, encoded
  exactly as `YYYY-MM-DD`. It has no timezone and never becomes an instant in stored state.
- `timed.instantMs` is the exact UTC instant as a non-negative integer Unix epoch millisecond.
  `timed.timeZone` is the canonical IANA timezone identifier in which the user specified or last
  edited the value. The timezone is retained for display and editing; changing the system timezone
  never mutates the stored instant or identifier.

The shared domain validates real calendar dates, safe integer milliseconds, and timezone identifiers.
It canonicalizes a timezone through the platform timezone database before storage. A local wall-time
picker must resolve its choice to one exact instant before calling the domain. If a wall time is
ambiguous during a backward DST transition, the UI must make the selected occurrence explicit; if
it does not exist during a forward transition, submission is rejected as `INVALID_DUE_VALUE`.
Adapters may not invent their own ambiguity policy.

## Today

Today evaluation takes two explicit inputs: `evaluationInstantMs` and a canonical IANA
`viewerTimeZone`. The domain derives the viewer's local calendar date, the exact start of that date,
and the exact start of the next calendar date. It performs calendar arithmetic in the viewer
timezone; it never assumes a day is 24 hours.

A task is in Today exactly when it is incomplete, not trashed, and either:

- all-day with `date <= viewerLocalDate`; or
- timed with `instantMs < startOfNextViewerDateMs`.

This includes overdue and due-today tasks. A timed task is overdue when its instant is before the
start of the viewer's current date. An all-day task is overdue when its date is before the viewer's
current date. Tasks without a due value, completed tasks, and trashed tasks are excluded.

All-day calendar meaning is intentionally stable when the viewer timezone changes. A timed value is
an instant, so its overdue/due-today classification may change when viewed in a different timezone.
Raycast, the menu bar, and MCP must call this same query with the same two inputs to receive the same
result and count.

### Today truth table

Unless a row says otherwise, the viewer timezone is `Australia/Melbourne`, the local date is
`2026-10-04`, and that DST-start date runs from `2026-10-03T14:00:00.000Z` inclusive to
`2026-10-04T13:00:00.000Z` exclusive.

| Due/lifecycle value                                          | Today result for every consumer |
| ------------------------------------------------------------ | ------------------------------- |
| No due value                                                 | Excluded                        |
| All-day `2026-10-03`                                         | Included as overdue             |
| All-day `2026-10-04`                                         | Included as due today           |
| All-day `2026-10-05`                                         | Excluded                        |
| Timed `2026-10-03T13:59:59.999Z`                             | Included as overdue             |
| Timed exactly `2026-10-03T14:00:00.000Z`                     | Included as due today           |
| Timed `2026-10-04T12:59:59.999Z`                             | Included as due today           |
| Timed exactly `2026-10-04T13:00:00.000Z`                     | Excluded                        |
| Any included due value with `completedAtMs` set              | Excluded                        |
| Any included due value with `trashedAtMs` set                | Excluded                        |
| All-day `2026-10-04`, viewer changes timezone                | Still means local October 4     |
| Timed value, viewer changes timezone                         | Reclassified from its instant   |
| Timed value on Melbourne's 25-hour DST-end date `2026-04-05` | Uses both calendar boundaries   |

The final row means the next boundary is the start of `2026-04-06` in Melbourne, not the first
boundary plus 24 hours. The same calendar-boundary rule applies to every timezone transition.

### Today ordering

Today has one total order:

1. overdue before due today;
2. effective due instant ascending, oldest first;
3. priority rank descending;
4. `position` ascending;
5. `createdAtMs` ascending; and
6. `id` ascending using bytewise comparison.

For ordering only, an all-day date's effective due instant is the start of that calendar date in the
viewer timezone. A timed value uses its stored instant. This puts an all-day due-today task at the
start of its day while preserving exact timed order and makes mixed due types deterministic.

## SQLite schema design

Schema version 1 uses SQLite `STRICT` tables, `PRAGMA user_version`, and the already validated
rollback-journal connection and migration policies. Migrations acquire `BEGIN IMMEDIATE` before
reading `user_version`, apply one version, set `user_version`, and commit. Connections enable foreign
keys before beginning a transaction. The following block is the exact disposable schema exercised by
the validation harness.

<!-- task-model-schema:start -->

```sql
BEGIN IMMEDIATE;

CREATE TABLE projects (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL CHECK (length(trim(name)) > 0),
  position INTEGER NOT NULL CHECK (position >= 0),
  created_at_ms INTEGER NOT NULL CHECK (created_at_ms >= 0),
  updated_at_ms INTEGER NOT NULL CHECK (updated_at_ms >= created_at_ms)
) STRICT;

CREATE TABLE sections (
  id TEXT PRIMARY KEY,
  project_id TEXT NOT NULL,
  name TEXT NOT NULL CHECK (length(trim(name)) > 0),
  position INTEGER NOT NULL CHECK (position >= 0),
  created_at_ms INTEGER NOT NULL CHECK (created_at_ms >= 0),
  updated_at_ms INTEGER NOT NULL CHECK (updated_at_ms >= created_at_ms),
  FOREIGN KEY (project_id) REFERENCES projects (id) ON UPDATE RESTRICT ON DELETE RESTRICT,
  UNIQUE (id, project_id)
) STRICT;

CREATE TABLE tasks (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL CHECK (length(trim(title)) > 0),
  notes TEXT NOT NULL DEFAULT '',
  priority TEXT NOT NULL DEFAULT 'none'
    CHECK (priority IN ('none', 'low', 'medium', 'high')),
  position INTEGER NOT NULL CHECK (position >= 0),
  project_id TEXT,
  section_id TEXT,
  due_kind TEXT NOT NULL DEFAULT 'none'
    CHECK (due_kind IN ('none', 'all_day', 'timed')),
  due_date TEXT,
  due_at_ms INTEGER,
  due_timezone TEXT,
  created_at_ms INTEGER NOT NULL CHECK (created_at_ms >= 0),
  updated_at_ms INTEGER NOT NULL CHECK (updated_at_ms >= created_at_ms),
  completed_at_ms INTEGER CHECK (
    completed_at_ms IS NULL OR
    (completed_at_ms >= created_at_ms AND completed_at_ms <= updated_at_ms)
  ),
  trashed_at_ms INTEGER CHECK (
    trashed_at_ms IS NULL OR
    (trashed_at_ms >= created_at_ms AND trashed_at_ms <= updated_at_ms)
  ),
  CHECK (section_id IS NULL OR project_id IS NOT NULL),
  CHECK (
    (due_kind = 'none' AND due_date IS NULL AND due_at_ms IS NULL AND due_timezone IS NULL) OR
    (
      due_kind = 'all_day' AND
      due_date IS NOT NULL AND
      due_date GLOB '[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9]' AND
      length(due_date) = 10 AND
      due_at_ms IS NULL AND
      due_timezone IS NULL
    ) OR
    (
      due_kind = 'timed' AND
      due_date IS NULL AND
      due_at_ms IS NOT NULL AND
      due_at_ms >= 0 AND
      due_timezone IS NOT NULL AND
      length(trim(due_timezone)) > 0
    )
  ),
  FOREIGN KEY (project_id) REFERENCES projects (id) ON UPDATE RESTRICT ON DELETE RESTRICT,
  FOREIGN KEY (section_id, project_id)
    REFERENCES sections (id, project_id) ON UPDATE RESTRICT ON DELETE RESTRICT
) STRICT;

CREATE INDEX projects_order_idx
  ON projects (position, created_at_ms, id);
CREATE INDEX sections_project_order_idx
  ON sections (project_id, position, created_at_ms, id);
CREATE INDEX tasks_project_fk_idx
  ON tasks (project_id);
CREATE INDEX tasks_section_project_fk_idx
  ON tasks (section_id, project_id);
CREATE INDEX tasks_inbox_order_idx
  ON tasks (position, created_at_ms, id)
  WHERE project_id IS NULL AND section_id IS NULL AND trashed_at_ms IS NULL;
CREATE INDEX tasks_all_day_today_idx
  ON tasks (due_date, position, created_at_ms, id)
  WHERE due_kind = 'all_day' AND completed_at_ms IS NULL AND trashed_at_ms IS NULL;
CREATE INDEX tasks_timed_today_idx
  ON tasks (due_at_ms, position, created_at_ms, id)
  WHERE due_kind = 'timed' AND completed_at_ms IS NULL AND trashed_at_ms IS NULL;
CREATE INDEX tasks_completed_idx
  ON tasks (completed_at_ms DESC, id)
  WHERE completed_at_ms IS NOT NULL AND trashed_at_ms IS NULL;
CREATE INDEX tasks_trashed_idx
  ON tasks (trashed_at_ms DESC, id)
  WHERE trashed_at_ms IS NOT NULL;

PRAGMA user_version = 1;
COMMIT;
```

<!-- task-model-schema:end -->

The database enforces storage types, non-empty basic text shape, priority membership, placement
nullability, parent existence and ownership, due-tag consistency, timestamp ordering, and restrictive
parent deletion. The shared domain additionally enforces canonical UUID v4 IDs, Unicode-aware text
trimming, real Gregorian dates, safe integer range, canonical IANA timezones, lifecycle transition
permissions, append/rebalance behavior, and monotonic operation time. These assignments are part of
the contract; an adapter cannot take ownership of them.

Positions and names intentionally have no uniqueness constraint. Equal values are valid and use the
documented tie-breakers. The Today indexes narrow active all-day and timed candidates; the domain
computes calendar boundaries and the priority rank rather than relying on lexical SQL ordering.

## Future implementation seams

The smallest future seams are:

1. Pure domain value validators and comparators for IDs, placement, due values, ordinary ordering,
   and Today evaluation.
2. Command tests for create, move, complete, reopen, trash, restore, section removal, and project
   removal against an in-memory repository contract.
3. One schema-version migration that runs the exact version-1 DDL under the validated migration lock.
4. Storage contract tests that execute each domain command against disposable SQLite databases and
   repeat the existing concurrent-startup and interrupted-write checks.

Raycast entry points, menu-bar rendering, and MCP handlers remain consumers of those seams. They do
not receive direct SQL access or alternative date and lifecycle rules.
